# Phase 4 Basic UI Implementation Plan

**Goal:** Connect authentication, Today, the book library, book detail/addition, and calendar to persisted user data.

**Architecture:** Follow DESIGN.md and the existing Phase 3 contract. Client Supabase Auth manages renewable bearer sessions; protected screens never load private data before authentication. Existing user-token APIs retain RLS. Domain calculations remain in Scheduler and server modules. Initial plan creation is a single RLS-scoped transaction; progress recording and replanning remain Phase 5.

**Tech stack:** Next App Router, React, Tailwind/shadcn primitives, Supabase Auth, Zod, existing Scheduler.

- [x] Add client auth/session provider, email/password login/signup, sign-out, protected layout, responsive shell and accessible controls. Show configuration/session/network failures as actionable states.
- [x] Add read-model API for owned books/plans/sessions and detail retrieval. Add validated plan preview and atomic first-plan save. Protect against duplicate plans, stale book baseline, overlapping shared time capacity and cross-user access.
- [x] Add Today, searchable resource library, detail with progress/forecast, Google/manual registration and initial-plan form, day/week/month calendar with mobile agenda. No fake analytics or nonfunctional progress buttons.
- [x] Test input/date/read-model and initial-plan APIs; test real Auth/DB transaction ownership and duplicate/rollback cases. Verify browser flow from login through manual book registration and plan creation, reload, Today/calendar, sign-out, and mobile layout.
- [x] Run workspace tests, types, lint, build, DB checks for new migration; update README/readiness and document Phase 5 handoff.

## Scope decisions

Authenticated UI is a client boundary using the existing bearer API instead of adding a second cookie authentication system. Search never blocks manual registration. Plan mode, daily pages, target date, timezone, weekday/time budget and initial reading speed are explicit inputs. First-plan saves populate existing goals/plans/availability_rules/schedule_sessions atomically. Shared availability/timezone cannot silently change while creating another plan; existing daily reservations are respected. Replanning and progress-event writes are intentionally excluded from this phase.

Implementation and verification results are recorded in WORKSPACE_UI.md and IMPLEMENTATION_READINESS.md §16.
