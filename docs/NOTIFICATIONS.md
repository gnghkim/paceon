# 매일 학습 알림

정한 시각에 브라우저 알림으로 오늘 할 분량을 한 줄 보낸다. 알림을 켜지 않아도 앱의 모든 기능은 그대로 동작하고, 못 채운 날을 따로 알리지 않는다.

## 사용자가 보는 것

**설정 → 알림**에서 시각을 정하고 **이 기기에서 알림 켜기**를 누른다. 브라우저 권한을 허용하면 그 기기가 등록된다.

구독은 브라우저마다 따로 만들어지므로 **기기마다 한 번씩 켜야 한다**. PC에서 켠 뒤 휴대폰에서 열면 **이 기기에서도 알림 받기**와 "등록된 기기 1대 · 이 기기는 아직"이 나온다. 켜짐 여부는 계정의 기기 수가 아니라 이 브라우저의 구독으로 판단한다. 계정 기기 수로 판단하면 두 번째 기기를 등록할 방법이 사라진다.

**알림 끄기**는 이 기기의 등록만 지운다. 다른 기기가 남아 있으면 그 기기는 계속 받고, 마지막 기기를 끌 때만 시각을 비운다. 읽은 기록과 계획은 그대로 남는다.

알림 문구는 `오늘 20쪽 · 영어 10분`처럼 예정된 것만 말한다. 둘 다 없으면 `오늘도 한 걸음 남겨 볼까요?`다. 못 읽은 분량이나 끊긴 연속일을 알리지 않는다. 알림을 열면 **오늘** 화면으로 간다.

iPhone은 홈 화면에 추가한 뒤 그 아이콘으로 열어야 알림을 받을 수 있다. Safari 탭에서는 받지 못한다.

## 보낼 때를 정하는 규칙

판단은 전부 DB의 `claim_due_notifications`에 있다. Worker가 여러 번 돌거나 두 개가 잠깐 겹쳐도 같은 사람에게 하루 두 번 울려서는 안 되기 때문이다.

- 사용자 시간대의 현재 시각이 `notify_at`을 지났고, 오늘 아직 보내지 않았고, 등록된 기기가 있으면 대상이다.
- 고르는 즉시 `notify_last_sent_on`을 오늘로 올린다. **전송이 실패해도 같은 날 다시 시도하지 않는다.** 알림은 놓쳐도 되는 정보이고 두 번 울리는 쪽이 더 나쁘다.
- 지정 시각에서 2시간이 지나면 그날은 건너뛴다. 자정 직전에 몰아 울리는 것보다 하루 거르는 편이 낫다.
- 시각을 바꾸면 `notify_last_sent_on`을 비워 새 시각으로 오늘부터 받는다.

시각 판정은 `private.notification_due`로 따로 떼어 고정된 시계로 검사한다. 시각끼리 더하면 자정을 넘을 때 값이 되감기므로(22:59 + 2시간 = 00:59) 지역 날짜에 시각을 붙인 타임스탬프로 비교한다. 이 계산을 잘못해 늦은 저녁 알림이 통째로 사라지는 버그가 실제로 있었다.

전송 결과는 `finish_notification`이 받는다. 404·410은 브라우저가 구독을 버린 것이므로 즉시 지운다. 그 밖의 실패는 횟수만 세고 열 번이 되면 지운다.

## 구성 요소

| 위치 | 역할 |
| --- | --- |
| `supabase/migrations/20261006000000_push_notifications.sql` | `push_subscriptions` 테이블과 RLS, 대상 판정·결과 반영 함수 |
| `apps/web/src/lib/push-client.ts` | VAPID 키 디코딩, 구독을 저장 형태로 변환, 지원 여부 판정 |
| `apps/web/src/app/api/push/route.ts` | 기기 등록·해제·개수 |
| `apps/web/public/sw.js` | `push`로 알림 표시, `notificationclick`로 열린 창 재사용 |
| `services/ai-worker/app/web_push.py` | RFC 8291 본문 암호화와 RFC 8292 VAPID 서명 |
| `services/ai-worker/app/notify_worker.py` | 대상 claim, 문구 작성, 전송, 결과 보고 |

암호화는 `cryptography`만 써서 직접 구현했다. 검사는 RFC 8291 §5의 예시 값으로 암호화한 뒤 그 문서의 사용자 키로 **복호화해 원문이 나오는지** 확인한다. 기대 암호문을 손으로 옮겨 적으면 옮긴 것이 맞는지만 확인될 뿐이다.

## 설정

VAPID 키 한 쌍이 필요하다. 만들기:

```powershell
node scripts/generate-vapid.mjs
```

공개키는 웹에, 비밀키는 Worker에만 넣는다.

| 위치 | 변수 |
| --- | --- |
| `apps/web/.env.local`, Vercel | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` |
| Worker `.env` (VPS의 `/opt/paceon-deploy/.env`) | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` |

`VAPID_SUBJECT`는 `mailto:` 또는 `https://`로 시작해야 한다. 푸시 서비스가 문제 생길 때 연락할 곳이다.

키가 비어 있으면 설정 화면은 "아직 알림 서버가 준비되지 않았어요"라고 알리고 발송기는 아예 돌지 않는다. 나머지 기능은 그대로다. **키를 바꾸면 기존 구독이 모두 무효가 되므로 사용자가 기기마다 다시 켜야 한다.**

공개키는 빌드 시점에 번들에 박히므로, Vercel에 넣은 뒤 **재배포해야** 적용된다.

발송 주기는 `NOTIFY_POLL_SECONDS`(기본 60초, 10~900초)다.

## 검증

- `pnpm test`: 키 디코딩과 구독 변환, 지원 여부 판정.
- `supabase test db`: 대상 판정(자정 경계 포함), claim이 하루 한 번인지, 실패·만료 처리, RLS와 권한.
- `pnpm test:ai:worker`: RFC 8291 왕복 복호화, VAPID 서명 검증, 문구 작성, 404/410과 일시 실패 구분, 설정 누락 시 정지.
- 2026-09-16 실제 확인: 로컬 프로덕션 빌드에서 알림을 켜 Chrome이 FCM 구독을 만들고 DB에 저장되는 것, Worker가 그 구독으로 실제 전송해 브라우저에 `오늘 20쪽 · 영어 10분`이 뜨는 것, 같은 날 두 번째 실행이 0건인 것, 끄기가 구독과 시각을 함께 지우는 것을 확인했다. 실제 휴대폰과 iOS는 확인하지 못했다.
